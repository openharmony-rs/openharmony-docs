## Setting Up a DLP Server

Currently, setting up a server generally involves implementing encryption/decryption and cloud-based authentication. It is recommended that you work with HarmonyOS developers to finalize the specific interaction fields. The overall process can be divided into the credential application stage, the file encryption stage, and the file decryption stage.

### Credential Application Phase
In enterprise scenarios, the credential application phase is embedded in the process of generating/opening a DLP file. It is separated here to explain the main operation process on the server.

1. Key initialization

    - Generate the server public/private key pairs (an Ed25519 key pair `serverSignPubKey` and `serverSignPriKey`, and an X25519 key pair `serverEncPubKey` and `serverEncPriKey`).

    - If the server already has the two key pairs above, there is no need to generate them again. The two key pairs are generated by calling the OpenSSL algorithm library.


2. Challenge response message (first cloud request)

    - Verify the account identity sent from the client by using the account identifier and account authentication information reported by the client.

    - Respond to the credential registration request from the client, and generate a random challenge by calling the OpenSSL algorithm library. The challenge is used by the client to subsequently generate the key attestation value (`keyAttestationValue`).

    - Return the challenge value and the algorithm version number to the client.


3. Credential application message (second cloud request)

    - Verify the key attestation sent by the device side, and check whether the challenge value in it is generated by the server.

    - Generate an ephemeral signing key pair, and use it to sign the signing and encryption public keys persistently stored on the server.

    - Generate a server certificate chain that contains the public key information and certificate chain material described above, and return it to the device-side client.


### File Encryption Phase

In this phase, the server performs exactly the same operations as in the credential application phase. The main purpose is to provide the server encryption public key `serverEncPubKey` to the device side.

### File Decryption Phase


1. Key initialization

    Same as the [credential application phase](#credential-application-phase). If keys already exist, there is no need to generate them.

2. Challenge-response message (first cloud request)

    Same as the processing steps in the [credential application phase](#credential-application-phase).

3. Credential application message (second device-cloud interaction)

    - Verify the key attestation uploaded by the device and check whether the challenge value in it was generated by the server. At the same time, obtain the temporary decryption public key.

    - If the server key version in the message uploaded by the device is inconsistent with the actual situation on the server, regenerate the server public key attestation material (same as the last two steps of the credential application phase, including the public key information and the certificate chain).

    - Use the server decryption private key to perform key agreement with the temporary decryption public key in the uploaded message, and use the agreed key to decrypt the policy ciphertext uploaded by the device to obtain the policy plaintext.

    - The server can process the obtained policy plaintext as needed, including modifying the plaintext content.

    - Generate a pair of temporary encryption/decryption public and private keys, use the temporary private key to perform key agreement with the temporary public key of the device side obtained from the certificate chain, and re-encrypt the policy plaintext with the agreed key.

    - Encapsulate the necessary information into a message and return it to the device-side client for decrypting the file and handling permission control.

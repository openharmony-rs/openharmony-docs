In cross-process invocation scenarios, the client usually needs to depend on the Proxy header file generated by the server at compile time to initiate interface invocation. When there are many interfaces or the server changes frequently, the client has to re-synchronize the header file and recompile each time, resulting in high maintenance costs. At the same time, static binding requires the invocation target to be fully determined at compile time, making it difficult to adapt to scenarios where the invocation target can only be determined at runtime.

Starting from API version 26.0.0, the system provides the client-side dynamic invocation engine ModularObjectDispatcher (for the related C API definitions, see [modular_object_dispatcher.h](../reference/apis-ability-kit/capi-modular-object-dispatcher-h.md)). It is created based on the connected remote Proxy object, allowing the client to query the type library metadata registered by the server at runtime (interface names, method signatures, parameter types, struct fields, etc.), and to resolve the member ID dynamically through the method name and then directly initiate IPC invocation, without depending on any interface definition from the server at compile time.

It is suitable for scenarios where the invocation target needs to be determined dynamically at runtime, such as a general-purpose script engine dynamically invoking remote methods, an automated testing framework automatically scanning and verifying all server interfaces, and a cross-version gateway service adapting to backend interfaces of different versions through metadata. It is not suitable for scenarios where the interfaces are fully determined at compile time and performance is extremely sensitive; in such cases, static Proxy/Stub should be used for direct invocation.

## Basic Concepts

- Dispatcher (ModularObjectDispatcher): the client-side dynamic invocation engine, created based on the remote Proxy object, providing type library metadata query and dynamic method invocation capabilities.

- Type Descriptor (TypeDescriptor): the metadata access handle obtained through the dispatcher, used to query information such as interfaces, methods, enums, and structs defined by the remote service.

- Type Library Metadata: the type description information generated by the server through the Taihe tool, defining interfaces, method signatures, parameter types, enum values, and struct fields. The dispatcher lazily loads this information from the remote end on first access.

- Variant: a general-purpose data container capable of storing values of multiple different types, distinguishing the actual stored data type through a type tag, used for parameter passing and return value reception in method invocation.

- Member ID (MemberID): the unique identifier of a method in the type library. After the client resolves the MemberID through the method name, it can use this ID to initiate dynamic invocation.

## Working Principles


The invocation flow of ModularObjectDispatcher consists of the following stages:

1. Connect to ExtensionAbility to obtain the Proxy object: The client connects to ModularObjectExtensionAbility to obtain the remote Proxy object (`OHIPCRemoteProxy*`), which serves as the communication foundation for subsequently creating the dispatcher and initiating dynamic invocation.

2. Create the dispatcher: Use [OH_AbilityRuntime_ModObjDispatcher_CreateMainServiceInstance](../reference/apis-ability-kit/capi-modular-object-dispatcher-h.md#oh_abilityruntime_modobjdispatcher_createmainserviceinstance) to create a dispatcher bound to the main service interface from the Proxy.

3. Get the type descriptor: It is recommended to first call [OH_AbilityRuntime_ModObjDispatcher_HasTypeDescriptor](../reference/apis-ability-kit/capi-modular-object-dispatcher-h.md#oh_abilityruntime_modobjdispatcher_hastypedescriptor) to confirm that the remote service supports metadata, and then obtain the TypeDescriptor handle through [OH_AbilityRuntime_ModObjDispatcher_GetTypeDescriptor](../reference/apis-ability-kit/capi-modular-object-dispatcher-h.md#oh_abilityruntime_modobjdispatcher_gettypedescriptor). This call triggers the type library metadata to be pulled from the remote end via IPC and cached locally, so subsequent queries directly hit the cache.

4. Query interface metadata: Based on the type descriptor, the client can traverse at runtime all interfaces, methods, structs (including field names and field types), enums (including enum value names and values) defined by the server, as well as the type library version and the main service interface name.

5. Get method parameter types and MemberID: Before invoking a method, query the type information of the return value and each input parameter through [OH_AbilityRuntime_TypeDescriptor_GetMethodReturnType](../reference/apis-ability-kit/capi-modular-object-dispatcher-h.md#oh_abilityruntime_typedescriptor_getmethodreturntype) and [OH_AbilityRuntime_TypeDescriptor_GetMethodParamType](../reference/apis-ability-kit/capi-modular-object-dispatcher-h.md#oh_abilityruntime_typedescriptor_getmethodparamtype), and resolve the method name to a MemberID through [OH_AbilityRuntime_TypeDescriptor_GetMethodMemberId](../reference/apis-ability-kit/capi-modular-object-dispatcher-h.md#oh_abilityruntime_typedescriptor_getmethodmemberid), so as to strictly construct Variant according to the type and avoid type mismatch errors.

6. Construct Variant parameters and perform dynamic invocation: Pass the MemberID and the constructed Variant parameters through [OH_AbilityRuntime_ModObjDispatcher_CallMethod](../reference/apis-ability-kit/capi-modular-object-dispatcher-h.md#oh_abilityruntime_modobjdispatcher_callmethod) to initiate the invocation. The dispatcher serializes the parameters and sends them to the remote end via IPC, then deserializes the return value into the output Variant.

7. Release resources: The dispatcher, type descriptor, various container handles, Variant, and TypeInfo objects must all be released by calling the corresponding interfaces according to the ownership rules.

## Constraints

- Before using ModularObjectDispatcher, ensure that the client has established a connection with ModularObjectExtensionAbility. For connection-related constraints and limitations, see Using ModularObjectExtensionAbility to Implement Modular Objects (C/C++).

- The server-side Stub must be generated through the Taihe tool. ModularObjectDispatcher relies on type library metadata to perform dynamic invocation. Only Stubs generated by the Taihe tool embed type library metadata; manually written Stubs cannot support dynamic invocation.

- The parameter and return value types of a method are defined by the server. The client must query them through metadata and strictly construct the Variant according to the types; otherwise, a type mismatch error is returned.

- When the connection is actively disconnected or the peer dies, the ModularObjectDispatcher becomes unavailable.

## Creating a Dispatcher Instance

The dispatcher is the entry point for client dynamic invocation. After creating the dispatcher, the client can query the server-side interface metadata at runtime and initiate invocation by method name. This section introduces how to create a dispatcher instance bound to the main service interface based on a connected Proxy object. The type library metadata is lazily loaded from the remote service when first needed.

Prerequisites: The client has connected to ModularObjectExtensionAbility and obtained the Proxy object. For details, see the "Connecting to ModularObjectExtensionAbility" and "Communicating with the Server Through Proxy" sections in Using ModularObjectExtensionAbility to Implement Modular Objects (C/C++).

The following steps assume that the `g_remoteProxy` object of type `OHIPCRemoteProxy*` has been obtained through the connection callback, and that the global variables `g_ModObjDispatcher` and `g_TypeDescriptor` are used to store the dispatcher and the type descriptor.

## Get Type Descriptor

The type descriptor is the access handle for querying the server-side interface metadata. After obtaining the type descriptor, the client can traverse all interfaces, methods, parameters, structs, and enums defined by the server, preparing for subsequent dynamic invocation by method name. This section introduces how to determine whether the remote service provides type library metadata and how to obtain the type descriptor handle.

1. Use the [OH_AbilityRuntime_ModObjDispatcher_HasTypeDescriptor](../reference/apis-ability-kit/capi-modular-object-dispatcher-h.md#oh_abilityruntime_modobjdispatcher_hastypedescriptor) interface to determine whether the remote service provides type library metadata. Only a server that supports dynamic interfaces can perform subsequent metadata query and dynamic invocation.

    <!-- @[modular_object_extension_dispatcher_hasTypeDescriptor](https://gitcode.com/openharmony/applications_app_samples/blob/master/code/DocsSample/Ability/ModularObjectExtensionDispatcherClient/entry/src/main/cpp/napi_init.cpp) -->

    ``` C++
    uint32_t hasTypeDescriptor = 0;
    ```

## Get the Parameter Types of a Method

## Perform Dynamic Invocation Through Dynamic Interfaces

This scenario is the core of dynamic invocation. Using the MemberID corresponding to the method and the constructed parameters, the client can initiate an IPC invocation at runtime and obtain the return value without binding to the server-side interface at compile time. It is suitable for scenarios where the interface can only be determined at runtime, such as general-purpose invocation frameworks, script engines, and dynamic testing tools.

Resolve the MemberID by the method name, construct the parameters, and then initiate the dynamic invocation. The MemberID can be queried from the TypeDescriptor through the [OH_AbilityRuntime_TypeDescriptor_GetMethodMemberId](../reference/apis-ability-kit/capi-modular-object-dispatcher-h.md#oh_abilityruntime_typedescriptor_getmethodmemberid) interface. For details, see [Query All Interfaces and Method Information Under Interfaces](#query-all-interfaces-and-method-information-under-interfaces).

Take invoking the `Add(int32_t a, int32_t b)` method as an example. Encapsulate the parameters into a Variant array, and initiate the invocation through [OH_AbilityRuntime_ModObjDispatcher_CallMethod](../reference/apis-ability-kit/capi-modular-object-dispatcher-h.md#oh_abilityruntime_modobjdispatcher_callmethod).

<!-- @[modular_object_extension_dispatcher_callMethod](https://gitcode.com/openharmony/applications_app_samples/blob/master/code/DocsSample/Ability/ModularObjectExtensionDispatcherClient/entry/src/main/cpp/napi_init.cpp) -->

``` C++
// Construct the parameters.
OH_AbilityRuntime_ModObjDispatcher_Variant params[2] = {
    {.vt = OH_ABILITY_RUNTIME_MOD_OBJ_DISPATCHER_VT_I32, .u.i32Val = 10},
    {.vt = OH_ABILITY_RUNTIME_MOD_OBJ_DISPATCHER_VT_I32, .u.i32Val = 20},
};

OH_AbilityRuntime_ModObjDispatcher_InputParams inputParams = {.rgvarg = params, .cArgs = 2};

// Invoke the method. memberId 17 is the MemberID corresponding to the Add method, which can be obtained through OH_AbilityRuntime_TypeDescriptor_GetMethodMemberId.
OH_AbilityRuntime_ModObjDispatcher_Variant result = {.vt = OH_ABILITY_RUNTIME_MOD_OBJ_DISPATCHER_VT_EMPTY};
int32_t methodErrCode = 0;
uint32_t memID = 17;
AbilityRuntime_ErrorCode err = OH_AbilityRuntime_ModObjDispatcher_CallMethod(g_ModObjDispatcher, memID,
    &inputParams, &result, &methodErrCode);
if (err != ABILITY_RUNTIME_ERROR_CODE_NO_ERROR) {
    // Framework-level error: IPC communication failure, parameter type mismatch, etc.
    OH_LOG_ERROR(LOG_APP, "add err:%{public}d", err);
    return nullptr;
}
if (methodErrCode != 0) {
    // Method-level error: the business error code returned by the remote method execution.
    OH_LOG_ERROR(LOG_APP, "methodErrCode:%{public}d", methodErrCode);
    return nullptr;
}
// result.u.i32Val is the return value (30).
int32_t addResult = result.u.i32Val;
OH_LOG_INFO(LOG_APP, "addResult :%{public}d", addResult);
// Simple types do not need to be cleaned up.
```

> **Description**
>
> CallMethod uses a two-layer error handling mechanism:
> - Framework-level errors (return value): issues at the framework layer, such as IPC communication, metadata loading, and parameter type validation.
> - Method-level errors (pMethodErrCode output parameter): the business error code returned by the remote method execution, where 0 indicates successful method execution.

## Passing Complex Type Parameters

When the server-side method parameters are complex types such as arrays, vectors, sets, maps, or structs, you need to construct the corresponding composite Variant for passing, so as to support invoking interfaces with arbitrary signatures. This applies to scenarios where batch data, key-value pairs, or composite structs need to be passed.

When method parameters contain container types (arrays, vectors, sets, maps) or structs, you need to first create the corresponding container instance and fill in the data, then wrap the container handle as a Variant parameter.

### Passing Array Parameters

Create an array through [OH_AbilityRuntime_ModObjDispatcher_ArrayCreate](../reference/apis-ability-kit/capi-modular-object-dispatcher-h.md#oh_abilityruntime_modobjdispatcher_arraycreate), and fill elements using [OH_AbilityRuntime_ModObjDispatcher_ArraySet](../reference/apis-ability-kit/capi-modular-object-dispatcher-h.md#oh_abilityruntime_modobjdispatcher_arrayset). The following example uses a two-dimensional array `array<array<i32,5>,5>` and is divided into three steps: creating the array, invoking the method, and parsing the result.

Create and fill the two-dimensional array: first construct the nested TypeInfo (inner `array<i32,5>`, outer `array<inner,5>`), then use `ArrayCreate` to create the outer array, create the inner arrays row by row, fill their elements, and set them into the outer array.

<!-- @[modular_object_extension_dispatcher_callTypeArray_build](https://gitcode.com/openharmony/applications_app_samples/blob/master/code/DocsSample/Ability/ModularObjectExtensionDispatcherClient/entry/src/main/cpp/napi_init.cpp) -->

``` C++
static OH_AbilityRuntime_ModObjDispatcher_ArrayHandle BuildMatrixArray(uint32_t arrSize)
{
    // Construct the nested array type information: inner array<i32,size>, outer array<inner,size>
    OH_AbilityRuntime_ModObjDispatcher_TypeInfo elemType = {.vt = OH_ABILITY_RUNTIME_MOD_OBJ_DISPATCHER_VT_I32};
    OH_AbilityRuntime_ModObjDispatcher_TypeInfo innerType = {.vt = OH_ABILITY_RUNTIME_MOD_OBJ_DISPATCHER_VT_ARRAY};
    innerType.u.arrayType.pElementType = &elemType;
    innerType.u.arrayType.size = arrSize;

    // Create the outer array, create the inner arrays row by row, fill their elements, and set them into the outer array
    OH_AbilityRuntime_ModObjDispatcher_ArrayHandle matrixArray = NULL;
    AbilityRuntime_ErrorCode err = OH_AbilityRuntime_ModObjDispatcher_ArrayCreate(&innerType, arrSize, &matrixArray);
    if (!CheckApiErr(err, "ArrayCreate outer")) {
        return NULL;
    }
    for (uint32_t i = 0; i < arrSize; i++) {
        OH_AbilityRuntime_ModObjDispatcher_ArrayHandle rowArray = NULL;
        err = OH_AbilityRuntime_ModObjDispatcher_ArrayCreate(&elemType, arrSize, &rowArray);
        if (!CheckApiErr(err, "ArrayCreate inner")) {
            OH_AbilityRuntime_ModObjDispatcher_ArrayRelease(&matrixArray);
            return NULL;
        }
        for (uint32_t j = 0; j < arrSize; j++) {
            // Fill the inner array elements
            OH_AbilityRuntime_ModObjDispatcher_Variant cell = {.vt = OH_ABILITY_RUNTIME_MOD_OBJ_DISPATCHER_VT_I32};
            uint32_t multiply = 10;
            cell.u.i32Val = static_cast<int32_t>(i * multiply + j);
            OH_AbilityRuntime_ModObjDispatcher_ArraySet(rowArray, j, &cell);
        }
        // Set the inner array into the corresponding position of the outer array
        OH_AbilityRuntime_ModObjDispatcher_Variant rowVar = {.vt = OH_ABILITY_RUNTIME_MOD_OBJ_DISPATCHER_VT_ARRAY};
        rowVar.u.parrayVal = rowArray;
        OH_AbilityRuntime_ModObjDispatcher_ArraySet(matrixArray, i, &rowVar);
        OH_AbilityRuntime_ModObjDispatcher_ArrayRelease(&rowArray);
    }
    return matrixArray;
}
```

``` C
static void ParseArrayResult(OH_AbilityRuntime_ModObjDispatcher_Variant *result)
{
    // Validate the return type, and traverse the two-dimensional array in a nested manner to read each element
    if (result->vt != OH_ABILITY_RUNTIME_MOD_OBJ_DISPATCHER_VT_ARRAY || result->u.parrayVal == NULL) {
        OH_LOG_ERROR(LOG_APP, "TestType_Array result type unexpected");
        return;
    }
    // Traverse row by row, and read the element value column by column in each row.
    uint32_t rowCount = 0;
    OH_AbilityRuntime_ModObjDispatcher_ArrayGetSize(result->u.parrayVal, &rowCount);
    for (uint32_t i = 0; i < rowCount; i++) {
        OH_AbilityRuntime_ModObjDispatcher_Variant rowVar = {.vt = OH_ABILITY_RUNTIME_MOD_OBJ_DISPATCHER_VT_EMPTY};
        OH_AbilityRuntime_ModObjDispatcher_ArrayGet(result->u.parrayVal, i, &rowVar);
        uint32_t colCount = 0;
        if (rowVar.u.parrayVal != NULL) {
            OH_AbilityRuntime_ModObjDispatcher_ArrayGetSize(rowVar.u.parrayVal, &colCount);
            for (uint32_t j = 0; j < colCount; j++) {
                OH_AbilityRuntime_ModObjDispatcher_Variant cell = {
                    .vt = OH_ABILITY_RUNTIME_MOD_OBJ_DISPATCHER_VT_EMPTY};
                OH_AbilityRuntime_ModObjDispatcher_ArrayGet(rowVar.u.parrayVal, j, &cell);
                OH_LOG_INFO(LOG_APP, "array[%{public}u][%{public}u]=%{public}d", i, j, cell.u.i32Val);
            }
        }
        OH_AbilityRuntime_ModObjDispatcher_VariantClear(&rowVar);
    }
}
```

``` C
static void ParseStructResult(OH_AbilityRuntime_ModObjDispatcher_Variant *result)
{
```

## Resource Release

All handles obtained through Create interfaces and Variant/TypeInfo returned through Get interfaces must be released when no longer in use to avoid memory leaks.

``` C
// Release the TypeDescriptor.
if (g_TypeDescriptor != NULL) {
    OH_AbilityRuntime_TypeDescriptor_Release(&g_TypeDescriptor);
}

// Release the dispatcher.
if (g_ModObjDispatcher != NULL) {
    OH_AbilityRuntime_ModObjDispatcher_Release(&g_ModObjDispatcher);
}
```

Resource release must follow these rules:

- Use [OH_AbilityRuntime_ModObjDispatcher_TypeInfoClear](../reference/apis-ability-kit/capi-modular-object-dispatcher-h.md#oh_abilityruntime_modobjdispatcher_typeinfoclear) to clean up the heap resources held by TypeInfo. After cleanup, the internal pointer is set to NULL and vt is reset to VT_EMPTY.

- Use [OH_AbilityRuntime_ModObjDispatcher_VariantClear](../reference/apis-ability-kit/capi-modular-object-dispatcher-h.md#oh_abilityruntime_modobjdispatcher_variantclear) to clean up the heap resources held by Variant (strings, container handles, etc.). After cleanup, the variant is reset to VT_EMPTY. Simple types (boolean, integer, floating-point) do not hold heap resources and do not need cleanup.

- All container Release interfaces set the handle pointer to NULL and support passing a NULL pointer.

- When a Variant is passed into container functions (such as ArraySet and MapPut), a deep copy is performed. The caller retains ownership of the original Variant and must release it separately.

- Variants returned from container functions (such as ArrayGet, MapGet, and CallMethod return values) are deep copies. The caller obtains ownership and must call VariantClear to release them.

- Do not call Clear on a shallow copy of Variant or TypeInfo; clear only one of them.
